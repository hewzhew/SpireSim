# 原生玩家的对局工作台与回溯

状态：首版已接通过程查看、当前游戏、持续暂停、返回点、返回和“回到刚才”。Rust 提供精确返回点
与恢复，原生插件的同一游戏 owner 协调模型与人工操作。逐提交回执与从旧模型步骤定位存档仍为
后续设计，不声称每条历史消息都可恢复。使用入口见 [dsh 插件](../../tools/dsh_player/README.md)，
底层接口见 [run-play](../../tools/run_play/README.md)。

## 职责

Rust 拥有精确游戏状态、RNG、恢复点、分支与恢复操作。Node 工作台负责在同一个会话连接上
排队执行与重连。dsh 拥有模型运行、会话日志和介入消息。浏览器只呈现这些事实与调用入口，
不复制游戏状态、不修改旧聊天记录，也不从模型步骤编号推算游戏节点。

游戏允许的选择交给操作者：进入精英、使用抽牌药、放弃奖励不附加策略确认。
来源失效、目的地不可达、动作不合法或执行结果未确认仍由各自 owner 返回实际原因。
恢复能力不替代动作合法性、精确身份与执行结果的核对。

## 过程与局面

过程记录保留模型尝试、工具输入和返回，以及人工介入发生的位置。失败尝试与撤回的打法
仍可查看。当前游戏区域始终读取正式 head；回溯后旧日志画面不冒充当前局面。

一条模型步骤可能只有查询，也可能包含多个分别提交的命令；一次 `commit` 还可能采用
整场战斗。因此“上一条消息”“上一个模型步骤”与“上一个可恢复的游戏边界”分别表示。
同一步的多个真正提交应能单独定位，单纯读取和模型文字不创建重复存档。

界面以“对局工作台”作为整体入口，包含过程记录、当前游戏和返回点。
返回点列出房间、回合、HP、金币和药水；后续才在过程中的游戏提交旁标出能否恢复到执行前。
名称和描述帮助定位，操作绑定 Rust 返回的精确目标与当前 head，不能靠描述匹配目标。

`back --list --json` 的 `run-play-return-points-v2` 返回药水稳定 ID（保留空栏位）与原有 `TaskEpisodeOutcomeV1` 终局结果。界面在渲染时取名称和完整句子，诊断消息保留原文；语言不进入来源、目标、checkpoint 或恢复校验。返回请求仍使用 `run-play-return-request-v1`，回执仍使用 `run-play-return-receipt-v1`。客户端与 Rust 程序应一起更新，不从旧版英文名称或终局文字反推身份。

首版显示仍保留的近期决策、楼层落点和具名点。过程列表只提供记录查看，不通过重放旧聊天猜
回退目标。后续扩展自动保留范围时再测量空间与清理成本。

后续的逐提交回执由工作台提供本次真正完成的提交、各提交前后位置和未确认部分，附在官方工具记录中。
界面不以 `isError` 推断游戏被改动，也不从终端报错文字重建提交。
明确在提交前拒绝的请求显示“未提交”；先成功再失败的命令组列出已完成的前缀；
已发送但没有确认的动作显示“结果未确认”，核对实际游戏后再继续。
读取、搜索、预演和保存标记不因产生了日志或元数据修订而被画成新的游戏打法。

## 返回操作

选中可恢复点后，一次操作完成以下流程：

1. 沿官方运行控制停止当前活动，核对活动已经结束及待处理消息；取消请求被接受不等于已停止。
2. 由游戏连接的实际 owner 取得独占修改权。人工与模型复用同一工作台队列；不另开写连接。
3. 核验返回目标仍保留，并核验界面查询时的正式 head 未被别的操作替换。
4. 保留被离开的当前终点，执行 Rust 恢复并重连，读取实际资源、选项与恢复后的版本。
5. 在官方会话过程里追加介入事实，界面标出从哪处返回到哪处。原记录保持原样。

实际恢复失败或结果不确定时展示实际错误与当前核对结果；不自动改选其他点，也不重发动作。
普通合法选择与正常回退无需再输入 `elite` 或 `!` 之类的确认词。

“回到刚才”应返回第 4 步保存的原终点。保留与删除由 Rust 管理；需要有界的自动保留策略，
不能把全部游戏副本和模型输入无限复制到新目录。
当前结构化返回已经用一个 `previous_endpoint` 保留被离开的终点，包含终局。
再次返回时替换这个自动保留点；具名点独立保留。普通 `back` 的保留策略沿原合同。

## 接续与试打

回退后默认停在恢复的局面，继续运行是明确操作。介入期间新消息可见但不得抢占游戏修改权。
恢复事实及最新局面交付给模型后，旧选项、旧搜索结果和前一分支的预测不再作为可直接执行的对象。
模型可以保留已经试出的知识；撤回游戏状态不会抹掉它看过的结果，也不重新随机化 RNG。

人工操作通过官方 commands 执行，使用已支持的 `command/run` 与 `command/done` 日志，结果保留
暂停事实与精确恢复收据；不写入持久化层无法读取的自定义必需事件。在官方 AgentLoop 同步发布
`running`、尚未调度 driver 时，暂停 owner 取消此次唤醒并保留 inbox，因此新消息不会被认领或进入
模型请求。人工写操作等待 driver 静止后进入官方 `runMaintenance`，再走同一个游戏工作台队列。
不另建模型循环，也不长期占用 maintenance。继续时核对实际局面、追加继续事实并显式唤醒。
这些事件还驱动地图与过程面板刷新；旧工具返回单独保留，人工事实不占用模型步骤编号。

后续候选流程是：保存共同起点，尝试 A，保存 A 的终点，返回共同起点尝试 B，比较真实结果，
选择仍可恢复的终点继续。私下 `preview` 的假想终点单独标识，不成为正式回退目标。

## 实施顺序与检查

先由 Rust 提供结构化的可恢复点查询与带来源的恢复请求，再把正式游戏提交的前后位置
绑定到官方工具记录。随后接入官方停止、独占修改与接续交付，最后增加界面操作和分支比较。
不从现有 `back list` 的终端文本搭建另一套恢复协议。

底层与原生 owner 的暂停、恢复、接续已实现。接下来补正式游戏提交前后位置的记录，再决定如何
从过程列表定位对应可恢复点；当前浏览器仅提交 Rust 列表中精确的 source 与 target。

检查应覆盖：从商店购买前返回、从精英进场前返回、多命令的部分成功、整场战斗提交，
以及恢复期间的模型取消与新消息。也要检查保留点失效、恢复失败、重新连接、重启后读取和空间清理。
只读过程检查不得执行模型或游戏动作；集成检查使用隔离游戏，并证明状态与 RNG 的恢复一致。
