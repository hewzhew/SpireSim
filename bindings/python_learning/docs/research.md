# Research interfaces

[Python interface](../README.md)

These interfaces expose exact-state experiments or constructed scenarios. The ordinary public-information training interface is documented in [Batched game API](api.md).

## Fixed-combat execution and branches

The opt-in `step_with_fixed_combat(options_json)` applies one already-chosen strategic action per active slot and settles any combat it enters using the selected exact-search backend (`portfolio` by default, or `whole_combat` for `sts_guided_search::solver::CombatSolver`). `fixed_combat_options_json()` supplies the current default options. This is an oracle experiment even when the strategic model receives only public features. The fixed policy first excludes a mugged exit when a rewarded exit strictly improves materialized resources without a sacrifice. The exact outcome frontier remains available for explicit branches. It then selects highest HP, fewest potions, shortest line, and producer order; its receipt records the executor revision. It does not claim best run value. Wall limits can affect which witnesses are discovered, so reproducibility requires saved plans and producer identity as well as seeds and options.

An `advanced` result contains the ordinary transition columns plus separate `fixed_combat_evidence_json`. Only the chosen strategic ordinals are model actions; decision-step counters include the executed combat inputs. A result with `status=unresolved` has an unresolved slot and evidence, **no transition or reward columns**, and leaves the whole batch and pending choices unchanged. Exceptions also leave this macro's batch unchanged. Earlier successful searches in an unresolved batch are private attempts, not committed trajectories. Combat exit stops at the real strategic/terminal boundary without claiming rewards or making subsequent choices. Combat sources are rejected. Restricted-potion environments require a never-potion executor.

`fallback_action_limit=None` stops on a search miss. An explicit positive limit instead plays the public legality bootstrap from the unchanged combat entry, recording its revision, source snapshots and executed ordinal paths separately from witnesses. A real defeat produces ordinary terminal loss rows; exhausting this action limit still returns unresolved and rolls back. Search errors and invalid witnesses never trigger this fallback. It is a fixed, weak rollout policy, not a proven strong combat teacher.

Executor policy is explicit per call and is not stored in state checkpoints. `sts_learning.fixed_combat` provides a Python controller with typed limits and separate transition/evidence results. It is an experimental component, not a drop-in online training environment: callers must explicitly choose fallback and treat any remaining unresolved result as an interruption. Successful-only episodes must not be presented as unbiased win-rate or policy-improvement estimates.

At an undecoded combat root, `fixed_combat_branches(slot_index, options_json)` searches with the same backend and privately exact-replays every sampled nondominated witness. It returns source identity, options and attempt evidence, `candidate_ordinals`, and independent single-slot `LearningBatchEnv` objects aligned with those ordinals. All source slots and pending choices remain unchanged. Branches start at the actual exit, before claiming rewards, with their real deck, relic counters, gold, HP and remaining potions; ordinary strategic control and fixed combat can continue them. No branch is preferred or adopted. This is Oracle counterfactual research, not an unbiased distribution or a run-value estimate. An empty witness frontier returns an empty environment list, not a defeat. Fallback rollouts are rejected, and the source potion restrictions are preserved.

`env.start_fixed_combat_research(slot_index, options_json)` retains the same whole-combat solver for incremental resource studies. Its process-local `FixedCombatResearch.advance_to(generation_work)` accepts cumulative work targets within the creation contract. Search work and remaining search wall time carry across calls; idle time, publication and continuation experiments do not reset them. Each call returns the same branch/choice surface as `fixed_combat_branches`, with cumulative work in `attempt_json` and per-call elapsed time. Repeating the consumed-work target publishes without more search. Targets below consumed work, zero and over-contract targets are rejected. Only `whole_combat` without fallback supports this method. Earlier environments and immutable choices remain independent after refinement; adoption still checks the unchanged exact source. This adds no automatic budget allocation, stopping criterion, resource score or strategic selection policy.

The returned `choices` list contains immutable `FixedCombatBranchChoice` objects aligned with those environments. After researching continuations, `env.adopt_fixed_combat_branch(choice)` exact-replays only the chosen source combat and returns its receipt and next decision token. It requires the same exact source at an undecoded root; errors leave the batch unchanged. Other slots' pending choices survive. Rewards and researched future steps are never adopted. Choices are process-local witnesses, not checkpoint payloads, model actions or assertions that the caller's selection is strategically best. Adoption receipt `elapsed_ms` measures replay, excluding earlier research.

The maintained caller adapter and fresh-study entry are documented in [the learning caller](../../../learning/README.md#fixed-combat-strategic-studies). Their execution-binding envelope lives outside this native checkpoint format; it requires the caller's matching runtime contract before state decode.

## Combat groups and captured roots

Combat-root artifacts contain game state, not the collector's learning action restrictions. Pass `allow_combat_potions=False` to `LearningBatchEnv.from_combat_root_artifact_bytes` for a potion-restricted experiment. The default is the full action surface. The selected restriction also applies after in-process slot checkpoint restores during Node-SL search.

At an undecoded combat root, `LearningBatchEnv.combat_group(slot_index, replicate_count)` creates a `CombatLearningBatchEnv` without exposing or reconstructing the run-control checkpoint in Python. Every replicate shares the exact root id and combat-state hash, keeps its own numbered episode lineage, and uses the same `decision_batch`, `choose`, and atomic `step` rhythm. At any later undecoded active decision, `group.capture_recovery_root(replicate_index)` may explicitly retain that one replicate as an opaque in-process `CombatLearningRecoveryRoot`. The object binds its fresh current-state root identity to the source group identity and replicate index, and `spawn_group(replicate_count)` derives a new same-root group without exposing the session. Partially decoded actions and terminal replicates are rejected. The group records no automatic history; bounded retention and replay verification remain caller-owned curriculum work. `recovery.combat_root_artifact_bytes(max_bytes=...)` persists that exact caller-selected boundary as one canonical opaque root. The returned bytes can be loaded by `LearningBatchEnv.from_combat_root_artifact_bytes` or passed to Rust search tooling; Python never maps observation-local monster indices back to private runtime entity ids. `group.combat_decision_audit_json(replicate_index)` is the read-only diagnostic companion to one current model row. It returns the complete ordered typed candidate surface, including card/potion identity and monster target semantics, or `None` after full action decoding or terminal completion. Symbolic selection rows retain their exact prefix and append/submit domain. This JSON never enters the semantic model batch, chooses an action, or exposes a runtime handle; the Python learning caller may use it only to align interpretable policy scores with the unchanged candidate ordinals. `group.root_context` is a frozen native `CombatLearningRootContextV1` generated once by Rust. It exposes only compact public root facts for corpus selection and stratification; Python does not reconstruct them from semantic feature ids, and the context is not copied into every decision row. `LearningBatchEnv.combat_root_contexts()` discovers every current undecoded combat root as `(slot_index, context)` pairs in one call without constructing a replicate group. Callers can therefore select a small corpus before paying the session-clone cost of `combat_group`. `LearningBatchEnv.public_run_contexts()` returns one compact read-only public context per slot: seed, typed boundary kind, act/floor, HP/max HP, gold, and concrete potion-slot identities. It copies no checkpoint and retains no history. This is an opt-in measurement boundary for evaluation and auxiliary targets; the bridge does not turn resource facts into a score or reward. `LearningBatchEnv.without_combat_potions(seeds)` creates the same whole-run environment while removing combat potion use and discard only from the model candidate surface. The lane changes neither simulator legality nor non-combat potion choices. Because the batch checkpoint schema does not yet bind that policy, this lane rejects cross-process checkpoint serialization instead of silently restoring as the ordinary `all` surface. A fresh batch may instead start from exact later-run combat boundaries via `LearningBatchEnv.from_combat_root_artifact_bytes(payload, expected_roots=..., max_bytes=...)`. The payload is the versioned opaque batch written by `.\scripts\ol.ps1 learning-root export`; Rust checks its byte bound, exact root count, canonical encoding, unique root identities, recomputed root identity/context, and active combat boundary before exposing any slot. Python never parses a production continuation or simulator checkpoint. Private branch cutpoint files are intentionally not accepted. Every combat step repeats the exact root id and combat-state hash. Its newly terminal rows have no run reward fields: they return aligned terminal kind, bridge-owned win, player HP, root/terminal actionable living-enemy HP, turn, potion, and card-play columns. Escaped, dying, and half-dead entities are excluded. The source run slot is unchanged. The Python caller can accumulate exactly one row per replicate and derive separate same-root leave-one-out win, player-terminal-HP-ratio, enemy-HP-progress, and potion-retention axes. Enemy progress remains diagnostic and does not change the maintained all-loss no-signal objective. The caller does not combine these facts into a default scalar score. This remains an execution primitive for caller-owned grouped objectives, not a trainer or a teacher. Smoke Bomb escape is terminal kind `Unresolved` with `terminal_won=false`. Post-combat screen state alone never turns an escape into a learning victory.

## Complete-turn demonstrations

`complete_turn_demonstration_semantic_batch(payload)` accepts one validated winning complete-turn demonstration JSON and returns the same semantic tables, plus candidate row splits, one demonstrated ordinal per decision, and aligned candidate evidence. Complete-turn rows encode the shared public root, ordered public actions, observed public successor, potion spend count, boundary, and typed completed milestones. They do not encode combat turn count, exact hashes, source paths, opaque guide ranks, or recall-support claims. The demonstrated ordinal identifies one replay-verified positive; unchosen candidates remain unknown and are exported as such rather than as negative labels. Ordinary softmax cross-entropy would silently convert those unknowns into negatives, so it is only a same-row carrier smoke unless a separate evidence owner has resolved the alternatives. This is an exact-branch research input contract, not a no-reload observation.

`replay_verified_winning_complete_turn_line(case_bytes, actions_bytes)` is the filesystem-free corpus boundary for complete-run captures. Rust decodes and exact-replays every `ClientInput`, rejects an unfinished/loss/trailing line, and groups inputs only at real next-player-turn or terminal-win boundaries. Each returned turn includes opaque serialized full-turn input JSON and every strict prefix JSON needed by the existing exact-successor alignment methods; Python never parses actions or reconstructs turn boundaries.

`CompleteTurnExactEnv.from_case_bytes(payload, allow_potions=...)` owns one in-memory exact combat position over that same surface implementation. `decision_batch()` returns a one-row batch in the ordinary scorer shape; `choose(ordinal)` consumes the observed surface and commits its exact successor. Terminal kind, HP, and turn count are control evidence, not model features. The environment performs no filesystem IO and exposes no checkpoint, RNG, or exact hash to Python. It exists for fixed-case exact-branch learning loops, not as a deployable public-information combat environment.

## Constructed campfires and card rewards

`LearningBatchEnv.constructed_campfires(recipes_json)` accepts 1..128 strict recipes for explicitly constructed Ironclad first-act boss campfires. Each recipe names seed, ascension, current/max HP, first-act boss, cards and relics; optional `gold` retains a declared public balance (0..1,000,000, default 0). Optional `potions` names slot-ordered potion IDs or `null` for empty slots; omitting it keeps empty inventory. Capacity comes from the core's ascension setup and Potion Belt hook; excess entries are rejected. These are declared inventory conditions, not attributed potion drops or pickup histories. cards allow upgrades and persistent instance parameters. The native owner creates a single campfire before the named boss and regenerates the complete legal candidate surface and all facts. This is a mechanism/condition diagnostic entry, not a natural-run source. Research artifacts must retain recipes, producer version and the declared constructed role. Rest or Smith still uses the normal engine when chosen; this does not certify a full-run policy.

`LearningBatchEnv.constructed_card_rewards(recipes_json)` supplies the same bounded diagnostic entry for Ironclad card choices at first-act floors 1..14. Each strict recipe has `loadout` (the campfire loadout fields), `floor`, and 1..8 `offers` with card id and upgrade count. Offers come from the core's red or colorless reward pools; upgrades are validated by the real operation. The default synthetic corridor contains ordinary fights followed by the F15 campfire and named Boss. Optional `corridor_rooms` explicitly names all 15 map-y0..14 rooms, ends in `RestRoom` and excludes Boss/Victory room types. It permits controlled first-Elite preparation contrasts without changing cards or generating natural history; omission preserves the original corridor. The native owner retains every offer, Skip and applicable relic options; choosing still uses normal reward settlement. Samples must declare this constructed source and retain the recipes and producer version.

## Bootstrap and privileged projections

`decision_batch(legality_bootstrap=True)` obtains the deterministic public legality bootstrap in the same atomic frame. It is coverage behavior, not a capability baseline, incumbent, combat continuation, or teacher. The aligned `legality_bootstrap_available` and `legality_bootstrap_ordinals` columns cover represented strategic roots, combat roots, and bridge-local symbolic selection rows. The bootstrap consumes the same sanitized observation and candidate semantics as the model; it cannot inspect exact RNG state, hidden draw order, runtime UUIDs, or exact successor states. It is an initialization aid only after its behavior has been evaluated across seeds, including cycles at reversible boundaries. Availability means a legal choice exists; it does not establish useful progress or teacher quality. `public_legality_bootstrap_manifest()` is the one-call inventory of its revision, experimental maintenance policy, covered decision domains, fallbacks, and known limitations; callers should not reconstruct that map by searching Rust owners.

For the public bootstrap, `decision_batch(legality_bootstrap=True, reward_exit_slots=[...])` supplies caller memory of committed Reward/Proceed choices. Those slots use the task actor's shared route ranking at a map overlay; the hint is read-only and has no effect at other sites.

`decision_batch(privileged_node_sl_oracle=True)` is a retained, separately privileged exact strategic-owner projection. It returns aligned availability plus complete ordinal paths selected by the exact strategic-owner crate. Multi-card run choices are represented as `family -> append... -> submit`; no UUID enters the Python payload, and every ordinal is checked again against the current candidate row before execution. This surface is neither the public bootstrap nor a deployable Node-Reload/NoSL actor. 

## Guided search experiments

`DistanceCombatSearch` and `distance_route_data` provide the optional [successor-distance experiment](../../../tools/guided_search/README.md#后继局面的距离启发试验). Numerical estimates are source-bound batches; Rust owns real transitions, resource facts, partial coverage and complete replay. They do not execute a model-selected gameplay action or change the existing batch controllers. The optional `lookahead_inputs` constructor argument defaults to zero; positive values enable short checks inside that same resident graph and caller budget. The separate `advance_forced=False` option lets single admitted choices advance without a source estimate. Real inputs, resource ledgers, interrupted work and all budgets remain in the same Rust core; it does not choose between alternatives. The opt-in `probe_immediate=False` mode checks one real input before source estimation, keeping resulting boundaries for later opening without repeating parent transitions. It supports forced advancement but rejects simultaneous positive `lookahead_inputs`. Missing boundary features remain absent in data. `ordering="total_inputs"` preserves g+h ordering; opt-in `"remaining_inputs"` orders by remaining distance, then used real inputs, then creation order. Ordering is fixed before work and reported separately from the frozen model. It changes exploration only, without changing replay or resource requirements.

The appended `probe_forced_boundaries=False` option requires both immediate probing and forced advancement. After the first input it classifies each exact boundary, continues single admitted choices, and stops at the next multi-choice source. This extends the strict one-input stopping rule, with every intermediate input/state and expenditure preserved under the same limits. Prepared boundaries are reused when opened. `probe_forced_transitions` counts these extra transition attempts as a subset of immediate/total attempts and is omitted when zero.

`estimate_probe_boundaries=False` can be enabled with forced probe boundaries. Completed probes then queue the prepared multi-choice successors for their own estimates, without a parent estimate gating admission. A selected successor starts its next probe; admission never probes recursively. Only the initial source is checked before its first estimate: queued successors have not yet checked their outgoing edges. Direct qualifying wins found during each selected probe are replayed before further inference. All limits, factual bounds and resource checks remain in Rust; prepared states are not charged twice.

The independent search crate also exposes the bounded experimental `GuidedCombatBatch` through this wheel. Its numerical schema, source binding and bounded task scope are described in [the local experiment](../../../tools/guided_search/LOCAL_LEARNING.md). It does not use the public semantic schema or fixed combat executor described below. Optional `starting_hp` declares a constructed HP intervention; `search_services` switches this ephemeral population to fixed-root search with numerical `guide` replies. Both modes use the same independent core and exact win replay. In search mode, `policy_rollout_steps` optionally assigns consecutive raw-policy expansions to new leaves before returning to PUCT; the shared total budget still accounts for every transition. `task="draw_select"` selects a separately versioned entity/action observation and an explicit constructed deck; the default `starter` task retains schema 1. Optional `deck=[(canonical_card_id, upgrade_count), ...]` supplies a full ordered recipe within the schema-2 admitted content and capacity. It is recorded as a fresh constructed intervention. No existing root/checkpoint is loaded by this API.

`GuidedCombatBatch.from_specifications(...)` uses the separate [entity contract](../../../tools/guided_search/ENTITY_LEARNING.md) for per-case constructed loadouts and variable-size entity/action rows. The same core owns execution and search; setup dictionaries do not enter high-frequency step IO.

The bridge still contains no policy, optimizer, automatic reset, or PyTorch dependency. Its semantic arrays are an input contract, not evidence that a particular model or learning objective is correct.
